STEP 01

Understand where your app runs

icare wraps a trained model in a Shiny application. A visitor enters predictors in a browser, an R process calculates predictions, and the application displays the results. Preparing a model, building its interface and hosting the application are separate steps.

→
Save RDS filesModel · preprocessing
→
Build app.RInputs · results · export
→
Host ShinyShare a browser URL

Use GitHub Pages for documentation and links; use shinyapps.io to run R. Adding app.R to GitHub Pages, or including a local Shiny call in a static Quarto book, does not create a hosted R service. About GitHub Pages ↗

Before you beginThis guide starts with a trained icare object. If you have not trained a model yet, first follow the book’s classification, subtyping or survival analysis chapter. The application loads the fitted object for prediction.
STEP 02

Prepare and record your environment

Start with the R environment used to train your model. Confirm that prediction works locally before preparing deployment. These templates were checked against a fixed commit of icare 1.1.0, using R 4.5.1. This is a reproducibility baseline, not a claim about the latest release.

R
install.packages("rsconnect")
packageVersion("icare")
packageDescription("icare")$RemoteSha
sessionInfo()
Installing the reference icare version in a new environment

Follow the package installation instructions to configure R and Bioconductor first. The commands below install icare and its direct dependencies. Install the optional learner packages required by your chosen template separately. Avoid upgrading all packages after fitting a model.

R
install.packages(c("remotes", "BiocManager"))
BiocManager::install("ComplexHeatmap", ask = FALSE, update = FALSE)
remotes::install_github(
  "YuLab-SMU/icare@7ff676a556721affeb6da6c36b3bb60fc24ca468",
  dependencies = NA, upgrade = "never"
)

Survival packages such as mlr3proba and mlr3extralearners may need to be installed from their upstream GitHub repositories. Preserve the versions and sources used during training; consult mlr3proba, mlr3extralearners and the icare installation instructions. These commands are not a complete environment lockfile for every operating system.

Use a Bioconductor release compatible with your R version. Run BiocManager::valid() to identify mixed package versions. The S4Vectors 0.46.0 version used in our deployment fix is not a universal requirement for every R installation.

Download and extract the starter kit, then set your working directory to icare-shiny-starter. Choose the application you need. The variable names below are examples: replace them with the fitted objects from your own training session.

R
# Classification: use your fitted model and training-stage preprocessing
saveRDS(model_obj, "apps/classification/model.rds")
saveRDS(preproc, "apps/classification/preprocess.rds")
# Only if no external preprocessing was used, save NULL instead:
# saveRDS(NULL, "apps/classification/preprocess.rds")

# Subtyping: sub_obj must be a trained Subtyping object
saveRDS(sub_obj, "apps/subtyping/model.rds")

# Survival: prog_obj must be a trained PrognosiX object
saveRDS(prog_obj, "apps/survival/model.rds")
Reuse fitted preprocessing and retain every predictorIf classification used scaling, transformations or imputation, reuse the object fitted during training. Do not fit preprocessing on new inputs or transform already transformed data a second time. Keep categorical predictors, such as sex, even when they are excluded from numeric scaling. Category values must match the training levels.

RDS objects may contain training records. Review their contents and data permissions before deployment. Do not place model files in www/ or a public GitHub repository. The starter kit contains no project models or training data.

STEP 04

Arrange files and create example inputs

Use relative paths. Each application has its own directory, and its app.R reads the model from that directory. The survival template runs a prediction check at startup, so generate and review www/example.csv before launching it.

Project structure
icare-shiny-starter/
├── apps/
│   ├── classification/
│   │   ├── app.R
│   │   ├── model.rds          # Add your fitted model
│   │   ├── preprocess.rds     # Add fitted preprocessing or NULL
│   │   └── www/example.csv   # Generate and review artificial inputs
│   ├── subtyping/            # app.R + model.rds + www/example.csv
│   └── survival/             # app.R + model.rds + www/example.csv
├── make_example.R
├── check_app.R
└── deploy.R

Run this command in a terminal from the kit root. Replace survival with classification or subtyping as needed.

shell
Rscript make_example.R survival

The script creates three artificial profiles using marginal quantiles and category values from the reference variables. They are for interface testing, not model validation, and may contain implausible combinations. Check units, ranges and category values. The first CSV column must contain unique SampleID values; the remaining column names must match the model’s predictors exactly.

Input modes: the classification template uses manual entry. Its example CSV provides values to copy into the form, not a batch-upload interface. The subtyping and survival templates support both manual entry and CSV batch upload.

STEP 05

Build app.R with icare

These are the complete app.R files included in the kit. Expand a template, save it in the matching application directory, and edit its title, description, units and citation. Different fitted algorithms may require additional learner packages.

Module 2 · Classificationapp.R

Uses the caret model structure from this tutorial. Predictors are read from the first fitted model; confirm that the input schemas of all exposed models are compatible.

apps/classification/app.R
library(shiny)
library(icare)
# Explicit imports also let rsconnect identify packages used by saved models.
library(caret)
library(C50)
library(glmnet)
library(kernlab)
library(klaR)
library(randomForest)
library(rpart)
library(MASS)
library(ipred)
library(bslib)
library(plotly)
library(jsonlite)
options(shiny.maxRequestSize = 10 * 1024^2)

model <- readRDS("model.rds")
preproc <- readRDS("preprocess.rds")
features <- setdiff(names(model@train.models[[1]]$trainingData), c(".outcome", model@group_col))
stopifnot(inherits(model, "Train_Model"), length(features) > 0)
deployment <- icare::ModelDeployment(
  model, preproc = preproc,
  class_labels = levels(model@split.data$training[[model@group_col]]),
  model_description = paste(
    "Describe your classification model and intended research use here.",
    "Enter the required predictors, select a model and click INITIATE ANALYSIS.",
    "The probability is a model output for research demonstration."
  )
)
# Include categorical predictors as well as numeric predictors.
# This template uses the caret training schema from the first fitted model.
deployment$preprocess_columns <- features
app <- icare::deploy_clinlab_app(deployment, title = "ICARE | Classification")
app

Module 4 · Survival riskapp.R

Includes the surv.ranger backend and the prognosis framework dependencies. Add the appropriate backend when using another survival learner. The startup check uses three artificial profiles.

apps/survival/app.R
library(shiny)
library(icare)
library(shinydashboard)
library(DT)
library(mlr3)
library(mlr3proba)
library(mlr3extralearners)
# icare checks these optional packages dynamically when prediction is requested.
# Declare them explicitly so rsconnect includes them in the cloud bundle.
library(mlr3tuning)
library(mlr3tuningspaces)
library(paradox)
library(mlr3learners)
library(tidyverse)
library(data.table)
library(ranger)
library(survival)
options(shiny.maxRequestSize = 10 * 1024^2)

model <- readRDS("model.rds")
stopifnot(inherits(model, "PrognosiX"))
manager <- icare::New_Prog_Manager(model)
# Exercise the actual prediction path in the deployed runtime before serving UI.
local({
  example <- read.csv("www/example.csv", row.names = 1, check.names = FALSE)
  result <- manager$prog_predict(example, cutoff_method = "median", return_scores = TRUE)
  stopifnot(nrow(result) == nrow(example), all(is.finite(result$risk_score)),
            all(!is.na(result$risk_group)))
  message("ICARE survival startup prediction PASS: ", nrow(result),
          " artificial profiles; scores=", paste(result$risk_score, collapse = ","))
})
features <- model@best.model$features
icare::use_app_theme_grey()
icare::set_prog_app_text(
  title = "ICARE | Survival Risk",
  citation_text = "Replace with your study citation."
)
app <- icare::launch_prog_deploy_app(
  manager, title = "ICARE | Survival Risk",
  var_dict = data.frame(Feature = features, Description = gsub("_", " ", features),
                        Units = rep("Replace with the actual unit", length(features))),
  project_info = list(
    abstract = paste("Describe your fitted survival model and study here.",
                     "Enter the required predictors or upload a batch CSV to obtain risk scores and risk groups.",
                     "Example CSV profiles are artificial and are provided for interface testing."),
    citation = "Replace with your study citation."
  )
)
app

The var_dict table uses Feature, Description and Units columns. Keep the real predictor names in Feature and provide clear descriptions and units. For subtyping and survival, use project_info for the study abstract and citation. The survival interface also supports use_app_theme_grey() and set_prog_app_text() for theme and text customization.

STEP 06

Test prediction and the interface locally

Run the automated checks from the kit root, then launch the application in R. check_app.R exercises the actual Shiny server, including prediction, output generation and downloads. Classification checks the first available model; subtyping defaults to NMF. Test every additional method you intend to publish.

shell
Rscript check_app.R survival
# Test each subtyping method you have actually fitted:
Rscript check_app.R subtyping nmf
Rscript check_app.R subtyping lpa
Rscript check_app.R subtyping kmeans
# Classification:
Rscript check_app.R classification
R
# In the R console, launch one application at a time
shiny::runApp("apps/survival")
# shiny::runApp("apps/classification")
# shiny::runApp("apps/subtyping")
  • Enter one artificial profile, run prediction and check the results for errors.
  • For subtyping and survival, also upload a CSV and check sample IDs, row counts and downloaded results.
  • Confirm that units, factor levels and missing-value behavior match the training workflow.
  • For survival, test median, tertile and custom cutoffs. Custom thresholds must be ordered, distinct numeric values.
  • Restart R and repeat the check to detect reliance on global variables or undeclared packages.

A working page does not prove prediction works. Automated checks also do not replace browser tests of clicking, uploading and downloading. A survival risk score is a model output; it is not automatically an event probability at a specific time.

STEP 07

Check deployment dependencies

rsconnect scans package calls in application code to construct a dependency manifest. Learner packages referenced by saved RDS models, and optional packages checked dynamically inside icare, may not all be detected from library(icare) alone. Dependency discovery reference ↗

R
deps <- rsconnect::appDependencies(
  appDir = "apps/survival",
  appFiles = c("app.R", "model.rds", "www/example.csv"),
  appMode = "shiny"
)
deps[, c("Package", "Version", "Source")]
required <- c("mlr3", "mlr3proba", "mlr3tuning", "mlr3tuningspaces",
  "mlr3learners", "mlr3extralearners", "tidyverse", "paradox",
  "data.table", "survival", "ranger")
stopifnot(all(required %in% deps$Package))
A deployment issue we encounteredModule 4 initially loaded its interface but failed when calculating risk. Successive runtime checks reported missing mlr3tuning, mlr3tuningspaces, mlr3learners and tidyverse. The complete template declares these packages explicitly and runs a startup prediction check. The deployment script also checks that the prognosis dependencies appear in the manifest.

Record the R, icare and learner package versions and their installation sources. If you use renv.lock, update it after validation and keep it consistent with the local library. Avoid deploying a new model with a stale lockfile. The kit does not include a universal lockfile for all models.

STEP 08

Deploy to your own shinyapps.io account

  1. Create a shinyapps.io account and note your account name.
  2. Retrieve the account configuration command from the Tokens page and run it only in your local R console. Never put real tokens or secrets in app.R, GitHub, screenshots or documentation.
  3. Confirm registration, then deploy the selected application from the kit root.
R
# First run the setAccountInfo(...) command provided by your account page
# in your local R console. This command lists registered accounts:
rsconnect::accounts()
shell
# Terminal: replace these placeholders with your own account and app name
Rscript deploy.R survival YOUR_ACCOUNT my-survival-app

The deployment script uploads only app.R, the model, the artificial example CSV and, for classification, the preprocessing file. It requests public access. Use your own account and a new application name. Do not reuse this project’s icare01 account name. The first deployment installs R packages on the server; build time depends on the dependencies and service conditions.

After deployment, open the actual URL returned by the tool in a signed-out browser session. Test manual prediction, supported batch upload and result downloads. An idle application may need time to wake up. Check your account plan for current usage and resource limits. Posit deployment guide ↗

R
# Read the logs for your application from the R console
rsconnect::showLogs(
  appName = "my-survival-app", account = "YOUR_ACCOUNT",
  server = "shinyapps.io", entries = 100, streaming = FALSE
)

The survival template logs ICARE survival startup prediction PASS after a successful startup check. This confirms that the server executed prediction on artificial inputs. Complete the browser interaction checks as well.

STEP 09

Link the application from GitHub or Quarto

Once the Shiny application is deployed, add a standard link to your documentation page. Replace the placeholder URL below with the real address of your application.

html
<a href="https://YOUR_ACCOUNT.shinyapps.io/my-survival-app/"
   target="_blank" rel="noopener">Open my Shiny application</a>

You can also embed the application in an iframe. Keep the direct link as a fallback because embedding behavior depends on browser and hosting policies.

html
<iframe
  src="https://YOUR_ACCOUNT.shinyapps.io/my-survival-app/"
  title="My survival risk application"
  style="width:100%;height:900px;border:0">
</iframe>

For a Quarto book, keep the static entry page in the source project, for example under review-apps/. Merge the resource rule into your existing _quarto.yml. Uploading only to the output directory may lose the page on the next render.

yaml
project:
  type: book
  resources:
    - review-apps/**

Add [Open the application](review-apps/index.html) to a chapter and publish through your normal Quarto workflow. Configure the GitHub Pages source branch or Actions workflow for your own site. Quarto resources reference ↗

STEP 10

Troubleshoot by symptom

SymptomWhat to check first
Works locally; fails on prediction in the cloudRead showLogs. Check dynamic dependencies, learner packages, versions and the deployment manifest. HTTP 200 only confirms a page response.
model.rds or example.csv cannot be foundCheck the application directory, relative paths, filename case and appFiles. The server cannot access an absolute path on your computer.
Missing predictors, category mismatch or unexpected predictionsCompare actual training fields and factor levels. Check original units, column names, fitted preprocessing and accidental double transformation.
CSV upload fails or returns the wrong row countUse unique, nonempty sample IDs in the first column. Match predictor column names and check encoding, missing values and file size.
Bioconductor installation or compilation failsRun BiocManager::valid(). Check R/Bioconductor compatibility, repositories, system dependencies and network access.
The application exits during startupInspect the startup prediction log. Missing dependencies, incompatible example fields or an incomplete model object can fail this check.
The iframe is blank or disconnectedOpen the Shiny URL directly. Distinguish embedding restrictions, cold starts, server errors and account resource limits.
A replaced model still gives old resultsVerify the deployment account, application name and local RDS file. Redeploy, close the old session and test again.

When reporting an issue, include R/icare versions, the object type, the action that failed and sanitized logs. Do not attach account tokens or real patient inputs.

Before sharing your URL

Ask a colleague without a local R installation to complete a prediction and download the result through the public link. Then add that link to your manuscript or project documentation.
